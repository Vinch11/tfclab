## A — rampe et valeurs avant / après

`buildPlanConfigFromDiagnostic` produit `volumeRamp` seulement si
`trainingLevel` est renseigné et `weeklyHours > 0`. Le libellé « Structure
Confirmé » du titre du PDF ne prouve pas la présence du niveau dans cette
configuration. La version highly_trained/rampWeeks=1 peut également conserver
le nominal par conception ; 120 min seul ne prouve donc pas une perte de config.

Chemin complet : `computeWeekQuotaEntry` →
`applySlFloorIndividualization` → `buildWeeklySlotLayout` →
`weeklyQuotas[w]` → `lastWeeklyQuotasRef` et `_weeklyQuotas` dans le payload →
serveur `applySLFloorEnforcement` / `applyReconciler` → réconciliation client →
`validateWeeklyQuotas`. Le serveur ne reconstruit pas la rampe : il lit les
floors reçus. Sans ce payload, `applySLFloorEnforcement` retourne explicitement
`[SL_FLOOR] skipped_reason=no_weekly_quotas_payload` et `applyReconciler`
retourne `[RECONCILER] skipped_reason=no_weekly_quotas` : dans ce chemin,
la réparation serveur n'était pas exécutée, elle n'était pas exécutée puis
inefficace. Cela ne signifie pas que le serveur imposait alors 120 min.
Le correctif présent rétablit cette transmission dans le chemin
semaine seule, dont le quota était jusque-là limité à la réconciliation client.

Exemple synthétique déjà testé en #398, pas données de l'athlète : trained,
80 %, plafond +10 %/sem, floors nominaux bike/run 120/90 min :
S1 95/70, S2 105/80, S3 115/85, nominal atteint S4. Sans rampe : no-op
strict 120/90. Les semaines race/taper et les facteurs de risque gardent
exactement les règles #398. Aucun coefficient nouveau.

Le PDF a été créé à 20:26:39 UTC, après la fusion #398 à 16:53:03 UTC.
Cela prouve seulement la chronologie de l'export, pas la version du navigateur,
la date de génération, le déploiement Edge Function ou la configuration utilisée.
Pour distinguer correction non exécutée / no-op voulu / correction inefficace,
il faut comparer la version chargée, `volumeRamp`, les logs
`[sl_floor_individualization]` et les floors sérialisés. Aucun déploiement n'a
été effectué pour tenter de le vérifier.

Le resolver modifie `title` et `details` **en place sur l'objet séance reçu**.

`before` contient jour/titre/durée/ID mais pas `details`. Le formateur commun
lit `repair.day` au lieu de `before.day`, et affiche des valeurs par défaut pour
les compteurs propres à d’autres réparations. Ainsi `details=""`, jour `?`,
`sameSportCandidates=?/?` et `nearest=[aucun]` ne démontrent ni séance vide,
ni jour perdu, ni nombre réel de candidates proches. En revanche le
`candidates=0` à la fin du motif provient bien du pool local de candidats
structurés, avant les filtres de durée/intensité/phase.

### Cause A3 : la table du prompt vidait le pool de réparation

`serializeCatalogForPrompt` produit actuellement :

```text
ID | Cat | Objectif | Intention physiologique | Phases | Durée cible | Zone-cible | Structure
```

`parseCatalogCandidatesFromDump` utilisait encore `cells[4]` pour la durée.
Cette cellule est devenue `Phases`, donc `parseDurationRange("base")` renvoie
null. `buildCandidatesByChunk` dérivait alors `allowedIds` de cette liste vide,
puis filtrait même les métadonnées complètes par ces IDs vides. Le défaut
précède les vérifications sportives : l’absence annoncée n’atteste pas une
absence réelle de fiches endurance suffisamment longues dans le catalogue.

Historique vérifié : la colonne Intention vient du commit `45988ae6` (PR #393,
23/10/2026) ; cette dépendance du pool au parseur legacy date de `353924e8`
(16/10). Aucun retour arrière sur la colonne physiologique ni sur les protections
introduites auparavant.

La correction utilise `extractCatalogIdsFromDump`, déjà utilisé pour le contrat
IDs autorisés de génération, indépendamment des colonnes de durée. Le pool
reste constitué exclusivement de métadonnées complètes dont l’ID est injecté.
Les gardes sport/phase/intention/intensité/contexte/prérequis sont inchangés.
Le parseur legacy n’est toujours admissible que sous son drapeau de test dédié.

Preuve croisée : une fixture anonyme partagée contient deux tables produites
par le vrai sérialiseur (standard et D+/Éviter). Deux tests Vitest vérifient
qu’elles correspondent toujours au format réellement envoyé. Les tests Deno
les consomment avec les métadonnées : **2 échecs / 4 succès avant correction**,
**6 succès après**, dans chaque miroir serveur. Les rejets restent critiques
pour phase/intensité incompatibles, absence de métadonnées ou fiche hors IDs.
Les 298 tests Deno de chaque fonction miroir passent localement.

Le défaut est démontré dans le code et reproduit le symptôme de pool vide.
Sans le payload et la version Edge Function du run, il n’est pas établi comme
l’unique cause de chaque ligne des captures. Le pool rétabli n’autorise pas à
remplacer une séance de force par une SL facile si l’équivalence sportive le
refuse ; la correction ne garantit pas que toutes les SL du plan deviennent
réparables et ne résout pas la confusion course officielle/simulation de S9.

### Cause E2 : le bandeau et la sauvegarde ne lisaient pas le même périmètre

`AIPlanViewer` affiche `plan.weeklyQuotaIssues`. `mergeWindowIntoPlan`
héritait de la liste du premier plan sans fusionner celles des fenêtres suivantes.
Le hook remplaçait parallèlement son état à chaque requête : la sauvegarde
reprenait donc les issues de la dernière fenêtre. Le nombre 66 lu à l’écran
n’est pas une preuve d’un audit intégral des 33 semaines.

La fusion agrège maintenant les issues existantes et celles de la fenêtre,
renumérotées en semaines globales, en conservant leur sévérité. Le hook est
synchronisé avec cette liste ; la sauvegarde utilise en priorité la liste du
plan affiché, avec repli legacy. Une régénération semaine seule recalcule les
issues sur son `MergedPlan` (durées structurées) et les mêmes quotas transmis,
puis réutilise le même mergeur. Seules les issues de la semaine effectivement
remplacée sont actualisées ; les autres critiques sont conservées. Sans nouveau
diagnostic calculé, une ancienne critique n’est pas effacée comme si tout était
conforme. Aucun seuil ni prescription n’est modifié.

Tests purs : les alertes de S1 locale des fenêtres suivantes deviennent S16 puis
S31 ; les critiques de S1 globale restent présentes et sont toujours converties
en erreurs de sauvegarde. Une fenêtre propre remplace seulement ses anciennes
issues ; une fenêtre sans diagnostic conserve les critiques existantes.
Sur le commit précédent : **2 échecs / 1 succès** ; après correction les trois
tests passent. Cette correction peut augmenter le nombre visible d’écarts en
exposant ceux des fenêtres qui n’étaient pas agrégées. Elle ne prouve pas que les
quotas initiaux ni les séances correspondant aux 66 écarts étaient pertinents.

C, la sélection initiale D, les quotas sportifs réels E et le thème S24 F restent
ouverts. Les captures sont désormais analysées ; il manque encore la configuration,
les catalogues/métadonnées et les états intermédiaires du run. Aucun nouvel appel
Gemini ni aucune modification des données réelles n’a été effectué.
