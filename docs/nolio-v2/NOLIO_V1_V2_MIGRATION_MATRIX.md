# TFCLab — Matrice de migration Nolio v1 → v2

Date : 24 octobre 2026. Document de décision, aucune migration exécutée.

## Références et méthode

- Code : `Vinch11/tfclab`, `main` figé au commit [`d736e4763da33eda21c9e56a27d587dbecf546b6`](https://github.com/Vinch11/tfclab/tree/d736e4763da33eda21c9e56a27d587dbecf546b6). Branche documentaire : `docs/nolio-v2-audit`, créée directement depuis ce commit, sans reprendre une branche de correctif.
- Contrat : fichier transmis `api-1.json` (nom local `1-api-1.json`), OpenAPI **3.1.0**, `info.version=2.0.0`, 4 872 654 octets ; SHA-256 **`db58f8670ff82d9f93a16bd645f39ed6a7e81aa107c89bde9622bf3b6222e853`**. Les 181 chemins, 301 opérations et 311 schémas ont été parcourus directement ; les 2 008 références internes sont résolues, sans référence manquante. Inventaires intégraux en annexes.
- Analyse statique : arborescence GitHub récursive, contenus TypeScript/TSX, fonctions Edge, migrations SQL, configuration et CI ; recherche transversale des références Nolio puis remontée jusqu'aux routes, rendus et actions. Le clone Git local échouant sur le proxy, lecture du code par le connecteur GitHub, toujours au SHA ci-dessus. Les fichiers pertinents ont été matérialisés localement ; ce dossier local n'est pas un clone Git complet.
- Les sources SQL établissent l'état **déclaré par le dépôt**, pas l'état de Supabase en production. « Actif » signifie chemin d'exécution atteignable dans le code, **pas preuve d'utilisation réelle ni de déploiement**. Aucun appel Nolio, Supabase de production, Gemini ou test avec données réelles.
- **A** : capacité explicitement documentée. **B** : capacité documentée soumise à consentement, scopes, rôle, abonnement, disponibilité du capteur ou conditions du fournisseur. **C** : forme ou garantie absente/ambiguë dans le contrat, à confirmer. Les recommandations sont des choix TFCLab, pas des promesses Nolio.

Les références `paths[/api/v2/…][méthode]` et `components.schemas.*` ci-dessous désignent des sections exactes du fichier transmis. Base v2 : `https://www.nolio.io`, slash final obligatoire.

## Ce qui fonctionne réellement dans le code actuel

Le nom « sync bidirectionnelle » de `AGENTS.md` est plus large que les chemins trouvés. L'existant combine OAuth, association d'athlètes, import de métriques et records, import de charge réalisée, sélection de fichiers d'activité, export de séances planifiées et import manuel de courbes. Il ne comporte pas de réconciliation générale des calendriers ni de consommateur de webhooks Nolio.

`src/App.tsx` rend `/` → `Index`, `/planning/ai-plan` → `AITrainingPlanPage`, `/diagnostic` → `DiagnosticPage`, `/diagnostic/tests` → `TestsPage`, `/planning/library` → `WorkoutLibraryBrowserPage`, `/training-load` → `TrainingLoadPage`, `/evolution` → `EvolutionPage`. `Index` monte `ConfigurationPage` dans son interface, même si le callback OAuth redirige vers `/configuration`, route absente de `App.tsx` à ce commit : risque de parcours de connexion incomplet.

## Matrice des dépendances v1

Toutes les requêtes de données v1 ci-dessous portent `Authorization: Bearer <access_token>` du coach connecté. L'entrée des fonctions est authentifiée par Supabase (`getClaims`, ou `getUser` au départ OAuth), sauf cron par secret partagé et callback externe. Les rafraîchissements utilisent `/api/token/`, `grant_type=refresh_token`, authentification Basic par client ID et secret côté Edge. Cette convention v1 n'autorise pas à réutiliser l'application sur v2.

## Changements transversaux et points à faire confirmer

1. Nouvelle application obligatoire ; arrêt v1 **30 juin 2027**, et `/api/v2/migration/ids/` répondra 410 ensuite. Jusqu'à 100 IDs par appel, coût `N+1`, mêmes scopes/visibilité ; `not_found` peut signifier absent, supprimé, mauvais type ou non visible. Convertir users/sports puis événements par athlète ; ne jamais déduire un ID opaque d'un integer.
2. Plus d'`id_partner` dans les schémas de création v2 ni de garantie d'en-tête d'idempotence trouvée. Publication avec réponse perdue = résultat ambigu ; aucun POST rejoué aveuglément.
3. Les schémas `workout.items` ne sont que `{type:object}`. Une énumération narrative de nœuds n'en donne pas les propriétés valides. Le contrat permet de conclure à l'existence du contenu structuré, pas de certifier une conversion complète step/repetition v1.
4. `/batch/` décrit un `confirm_token` dans le texte et son obligation **via Nolio MCP**, mais `BatchResponse` ne le déclare pas. TFCLab REST doit imposer sa confirmation côté serveur sans supposer une garantie de token MCP. Le texte annonce `stale_preview` : vérifier le mécanisme applicable REST ; ajouter contrôles de révision systématiques.
5. Schéma streams marque `custom_laps`, `dynamic_streams`, `restriction` requis alors que le texte les dit omis dans certains cas ; `MetricsHRVMeasure` ne déclare pas `raw` alors que `with_raw=true` promet les RR. Accepter les omissions explicitement décrites, demander corrigendum, ne pas désactiver toute validation.
6. `PlannedTrainingCreateRequest.rpe` décrit 0–10, lecture 1–10 ; tester/faire clarifier le zéro. Tant qu'incertain, prescrire 1–10 ou absent.
7. Le texte du securityScheme OAuth dit « partner only », `info.description` documente aussi l'application d'équipe OAuth. L'application d'équipe est explicitement décrite, mais modalités du PAT d'administration pour une app OAuth/équipe à confirmer avant exploitation des webhooks/users.
8. Quotas horaires/journaliers dynamiques, non chiffrés contractuellement. Aucun plafond fixe par abonnement à inventer. Accès API actif du propriétaire, consentements et restrictions des connecteurs conditionnent disponibilité et push.
9. Liste records : `has_more=false`, pas une pagination ordinaire. HRV : tableaux bornés non paginés. Fenêtres calendaires inclusives, sans flux global `updated_since` documenté : réconciliation par fenêtres + événements, pas simple watermark de date de séance.
10. Données réalisées : `/real/trainings/` exclut les compétitions et les jambes multisports pour éviter le double comptage. Ne pas annoncer un endpoint « tout calendrier réalisé » unique.
