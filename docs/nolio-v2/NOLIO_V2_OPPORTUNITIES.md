# TFCLab — Opportunités Nolio v2 et données exploitables

Audit au 24 octobre 2026, référence et limites dans la [matrice](NOLIO_V1_V2_MIGRATION_MATRIX.md). Les propositions ci-dessous ne sont pas implémentées. A = explicite au contrat ; B = documenté mais soumis aux accès/disponibilité ; C = à confirmer. Une capacité A n'annule jamais les conditions B d'un utilisateur donné.

## 1. Inventaire des univers : ce que l'API apporte réellement

| Univers | A : explicitement documenté | B : conditions | C : ne pas présumer |
|---|---|---|---|
| Application, accès | app/introspection, PAT, OAuth, app/users, gestion webhook ; conversion IDs jusqu'au 30/06/2027 | App v2 neuve, scopes effectifs, API propriétaire active ; PAT pour users/webhook ; partenaire soumis à examen | Migration des autorisations v1, idempotence REST, provisioning PAT admin équipe |
| Athlètes, groupes, équipes | me/athletes, me/groups, team/groups, team/teams, membres/archives/invitations/pauses | Athlète coaché, consentement, rôles manager/assistant, isolation app équipe | Être listé ne donne pas accès aux données ; archives pas lisibles comme athlètes gérés |
| Sports et zones | Catalogue spt, profils spu, zones finales, wrappers, modèles, activation/édition de zones | Sport actif ; sport compatible workout ; scopes de référence ou settings ; write explicite pour mutation | Équivalence zones Nolio et domaines LT1/MLSS/VO2max ; stabilité d'une clé de métrique renommable |
| Calendrier planifié | Trainings, competitions, cycles, notes, messages, quizzes, récurrence, révisions ; charges projetées | planned:read/write/delete distincts, autorisations athlètes et équipe ; événements multi-athlètes non éditables | Ordre natif d'un brick, annulation identique à séance non réalisée, atomicité de tout un plan |
| Séances structurées | workout array ; step/repeat/exercise/superset/emom/for_time/amrap nommés ; exemple step en zone | Sport structurable et cibles disponibles ; actualisation des montres au PATCH | Schéma des nœuds et cibles complexes absent ; support montre précis non garanti |
| Bibliothèque et modèles | Catégories, trainings/competition frames, exercices, plans, contenus et apply ; modèle sans date et éléments en week/day | library scopes ; bibliothèques personnelles/équipe ; assistants exclus des bibliothèques d'équipe sur ces routes | Pas de génération IA par Nolio ; pas de transaction universelle de publication template+application |
| Réalisé, capteurs | Trainings et competitions séparés ; planned linkage ; streams et laps ; import de fichier possible | real:read ; capteurs et fichier existants ; restriction du fournisseur ; pas de contournement | Fréquence uniforme d'échantillons, toutes moyennes sur objet training, enrichissements qui n'existent pas |
| Statistiques et records | Catalogue de charts ; stats agrégées ; records puissance/allure/FC/couple/vitesse verticale/cadence ; fenêtres cataloguées | Données effectivement présentes ; throttle records 20/min ; sports et unités | Record à durée arbitraire, record d'ascension sur N mètres de D+, record = test maximal validé |
| HRV et métriques | Items/values/computed, RMSSD quotidien, mesures guidées valides et indices | metrics:read ; sources autorisées ; tableaux HRV bornés ; managed athlete en lecture seule records/HRV | Tous appareils exposent RR ; HRV nocturne = mesure guidée ; score récupération universel |
| Retours | Debrief RPE/feeling/comment/questions ; résultats de questionnaires planifiés | real:read, réponse athlète existante ; conventions de questions propres à l'équipe | Fatigue, sommeil, douleurs standardisés pour tous ; webhook quiz_results inexistant au catalogue |
| Webhooks | Un callback par app, signature, retries, catalogue d'événements, access.ended | Configuration active et consentements/scopes ; accès API propriétaire ; PAT admin | Rejeu historique garanti, ordre de livraison, livraison exactement une fois |
| Lots et récupération | ≤100 opérations planned/library, dry_run rollback, résultats par opération ; recovery et undo de lots | Quotas N+1 par appel ; undo compte exécutant+delete scopes+fenêtre+visibilité ; team-owned bloqué | Lot atomique ; updates annulables ; token MCP déclaré dans schéma REST |
| Billing, marketplace, messagerie, administration d'équipe | Routes nombreuses et inventoriées en annexe de la matrice | Scopes/rôles additionnels, paiements refusés app équipe, conversations visibles à leurs participants | Pas une raison d'élargir TFCLab maintenant ; aucun accès ni envoi demandé dans cet audit |

## 2. Catalogue des données pour « prévu → réalisé → réponse »

Toutes les routes de ce tableau commencent par `/api/v2/`. Les métriques observées ne sont pas des diagnostics. Une valeur null/restricted ou une fenêtre incomplète doit apparaître comme telle dans l'interface, pas comme zéro ni comme repos.

| Donnée / champs exacts | Source et granularité | Nature | Conditions, limites et usage TFCLab |
|---|---|---|---|
| Date, sport, durée, distance : `date_start`, `hour_start`, `sport`, `duration.value/unit`, `distance.value/unit` | `real/trainings/`, `real/competitions/` ; séance | Observée ou déclarée selon `source` | real:read, athlète autorisé ; durée lue en s, distance en km ; source restreinte peut nuller mesures. Base descriptive, pas intensité supposée |
| Données prévues : `date_start`, `time/moment`, durée/distance, `workout`, `rpe`, `load` | `planned/trainings/`, `planned/competitions/`, détail pour workout | Prescription ou charge dérivée | planned:read ; stocker version approuvée et calendrier courant ; une liste ne contient que has_structured_workout pour contenu |
| Lien prévu/réalisé : `planned` | Séance réalisée, référence ptrn ou pcmp | Liaison déclarée par Nolio | Peut être null ; filtre planned documenté. Aucun rapprochement automatique uniquement date/titre ; gérer plusieurs réalisées liées, doublons et courses |
| FC : `stream_heartrate`, `units`; laps `stats.heartrate_min/avg/max` | `real/trainings/{id}/streams/` et `/laps/`, compétitions symétriques ; échantillon / lap | Signal observé et agrégat dérivé | Capteur présent ; 204 sans fichier, [] stream absent ; pas de champ FC moyenne de séance garanti sur RealTraining. Calcul local pondéré par temps si nécessaire et contrôlé |
| Puissance : `stream_watts`; laps `watts_avg`, `watts_avg_with_zeros`, `watts_max`, `np` | Même routes ; échantillon / lap | Mesure et agrégats | Unités W ; moyenne hors zéros ≠ moyenne zéros inclus. NP dérivée, pas observation directe ; ne pas appliquer mêmes références à toutes disciplines |
| Cadence : `stream_cadence`, laps `cadence_avg/max` | Échantillon / lap | Mesurée et agrégée | `ppm` course deux pieds, `rpm` vélo, `cpm` aviron/kayak, `strokes/min` natation ; ne pas multiplier la cadence de course arbitrairement |
| Vitesse/allure : `stream_pace`, `stats.pace_avg/max`, `gap_avg/max` | Streams/laps | Mesurée/dérivée | Stream pace = **m/s**, laps et records = s/km, s/100m, s/500m ou km/h selon sport. GAP est une estimation ajustée à la pente |
| Distribution : `time_in_zones.heartrate/watts/pace/cadence/gap/va` | Événement détail ; liste avec `time_in_zones=true` ; statistiques de zones | Dérivée des signaux/configurations | Secondes par stream/zone ; streams sans données omis ; somme peut différer de durée séance ; conserver définition de zones utilisée |
| RPE : `debrief.rpe`; prévu `rpe/show_rpe` | Après séance, déclaré 1–10 ; null si non saisi, zéro stocké normalisé null | Déclaration subjective | Pas de remplissage automatique ; `show_rpe=false` masque la cible à l'athlète ; comparer prévu/réalisé en contexte, pas inférer un seuil physiologique |
| Sensation et texte : `debrief.feeling/comment/questions` | Séance, feeling 1–5 ; commentaire athlète et réponses custom | Déclaration subjective | Débrief Nolio ≠ ancien FeedbackNolio local ; noms/échelles de questions non standard. Réactions du coach ailleurs dans messages/conversation ; pas nécessaires à P0 |
| Questionnaires : `RealQuizResult.items`, `quiz_planned`, `quiz_type`, `is_confirmed`, `comment` | `real/quiz_results/` et détail ; formulaire daté | Déclaration structurée | real:read ; établir mapping question/échelle ; pas de score fatigue/sommeil universel. Relecture périodique, aucun événement quiz_result nommé |
| Coggan : `load.coggan`, `load.coggan_source`, `coggan_load` | Séance réalisée/prévue | Estimation dérivée ou saisie manuelle | Origines manual/workout/power/pace/heart_rate/rpe ; `coggan_load` override manuel. Valeur 0 lue null ; pas de substitution automatique par Foster |
| Foster : `load.foster` | Séance, minutes×RPE | Dérivée subjective | Dépend durée et RPE ; null si manque. Unités non identiques au TSS ; si Coggan source=rpe, deux champs ne sont pas deux preuves indépendantes |
| CTL/ATL/TSB et charge du jour : `fitness`, `fatigue`, `form`, `load` | `real/training-load/` jusqu'à aujourd'hui ; `planned/training-load/` projection dès demain ; points journaliers | Modèle Coggan Nolio | real:read / planned:read séparés ; modèle `coggan` seul, TRIMP annoncé futur et non accessible actuellement. Paramètres/hypothèses ne remplacent pas le modèle TFCLab |
| RMSSD : `value`, `unit`, `date`, `hour`, `source`, `restriction` | `metrics/hrv/rmssd/`, quotidien, dernières valeurs d'abord | Mesure importée ou saisie | metrics:read ; limit défaut 15 max 366 ; hour peut être ''. Oura/Strava/Whoop masquent value/description selon texte ; Huawei/Zepp restrictions additionnelles **MCP**. REST n'est pas MCP |
| Mesures HRV guidées : rmssd/sdnn/pnn50/hr_mean/rr_mean/serenity/total_power/lf_power/hf_power/ratio_lf_hf, method/device | `metrics/hrv/measures/` ; par mesure VALID uniquement | Indices dérivés d'une mesure | metrics:read, 90 j par défaut sans from, plafonds 366/31 raw. RR promis par `with_raw`, mais propriété absente du schéma : C pour forme et unité. Pas de diagnostic autonome LF/HF |
| Métriques de référence : item `id/key/unit/is_wb_compatible/formula/computation`, value `value/source/restriction` | `metrics/items/`, `metrics/values/` ; valeur datée | Mesurée, déclarée ou formule selon item | Le catalogue réel décide si poids, FTP, VMA, CSS, VO2max ou fatigue sont présents ; le contrat ne garantit pas ces séries pour chaque athlète. Clé target dérivée du nom, donc renommable |
| Métriques avancées : `rows`, `period`, `is_current` | `metrics/computed/?item=mti_…` ; jour/semaine/mois/année/saison | Agrégat d'activités | Item computation non-null ; pas de valeur correspondante dans metrics/values ; bornes élargies aux périodes entières, période courante incomplète ; max fenêtre 1825 jours |
| Records : `value/unit/date`, cat/record_type/inner_val, training/sport optionnels | `metrics/records/` ; meilleur effort par fenêtre catalogue | Extrême dérivé d'enregistrements | Catégories ppr/phrr/par/ptr/pvar/pcadr, time en s/distance en m ; fenêtres découvertes, pas 17 min arbitraire ; aucune date/id source parfois ; 20 req/min ; effort pas nécessairement maximal ni capteur fiable |
| Progression agrégée : catalogue dimension/measure, stats `rows` | `real/stats/charts/`, `real/stats/` ; agrégat par sport/tag/zones/feeling/rpe/details | Dérivée | Catalogue filtré selon données disponibles ; ne pas inventer une chart absente. Ne pas comparer agrégats de définitions différentes comme une évolution de performance |
| Fichier et compléments : `file_url`, dynamic_streams, custom_laps | Détail / streams ; fichier et échantillons | Données source, indices supplémentaires si appareil | URL temporaire nullable, restrictions légales ; respiration/smO2/glucose seulement si enregistrés et autorisés, pas promesse d'accès universel |
| Modification / suppression | revision et webhooks planned/real *updated/*deleted ; comparaison des scans complets | Événement de gestion | Pas d'historique complet garanti ; delete webhook objet réduit, pas motif sportif. Ne pas réintroduire une suppression distante par réexport |
| Séance non réalisée / annulée | Aucun statut universel d'adhérence confirmé dans PlannedTraining/RealTraining | **Inférence TFCLab à confirmer** | Absence de réalisé peut venir d'un retard import, absence d'accès, restriction ou mauvais lien ; « à vérifier » avant « non réalisée », annulation confirmée par coach |

Les restrictions des activités réalisées s'expriment par `restriction.{code,source,message,doc,fields}` et les champs masqués ; une mesure null hors de cette liste est simplement absente. Les filtres sur durée/distance/dénivelé masqués **retirent les activités de la page** : l'import d'exhaustivité ne doit pas filtrer sur ces mesures. En streams restreints, tableaux vides, fichier null, device laps retirés et statistiques des laps manuels nulles ; ne pas tenter d'en reconstruire le contenu par d'autres endpoints. La politique exacte de tous agrégats/records issus de connecteurs restreints doit être confirmée (C), pas supposée équivalente à la redistribution des fichiers.

## 3. Feuille de route de valeur

Complexité : S = adaptateur/écran limité, M = plusieurs modèles et traitements, L = concurrence/produit ou validation scientifique importante. Estimations relatives, sans engagement de délai avant spécification des workouts et accès.

| Fonctionnalité et priorité | Valeur concrète coach | Données requises / faisabilité | Complexité et dépendances | Risques / garde-fous |
|---|---|---|---|---|
| **P0 — Connexion fiable et export prévisualisé** | Le coach publie ce qu'il a réellement validé, sur le bon athlète et aux bonnes dates | planned, sports/zones, batch/dry_run, revisions (A/B) ; structures complexes C | L ; auth/mappings, fidélité adaptateurs, approbation et journal d'opérations | Mauvaise cible, doublons, demi-publication ; blocages explicites, résultat par séance, jamais publication IA automatique |
| **P0 — Tableau prévu/réalisé par athlète et discipline** | Voir rapidement quelles prescriptions ont été suivies et où consacrer l'entretien athlète | planned + real trainings/competitions, planned linkage, durée/distance/debrief/load (A/B) | M ; import complet, mapping sports, couverture et provenance | Retards/restrictions assimilés à non-adhérence ; afficher « inconnu », activités non rapprochées et calendrier courant vs publié |
| **P1 — Écarts significatifs de volume/intensité/charge** | Prioriser les cas où une semaine trop longue, trop intense ou trop courte mérite discussion | Durée/distance, time_in_zones, load/source, RPE ; A/B | M ; dashboard P0, baselines par sport, règles explicites coach | TSS/Foster confondus, zones différentes, fausse précision ; seuils contextualisés et confiance, pas seuil médical universel |
| **P1 — Ajustements proposés des séances futures** | Présenter des choix concrets après une charge réelle inattendue ; le coach gagne du temps sans perdre la décision | Écarts, retours, calendrier futur, contraintes du plan, doctrine TFCLab ; API A/B, décision interne | L ; phases 2–4, stabilité des données et validation métier | Réagir à un signal isolé, annuler un objectif ; diff et justification, validation explicite, nouvel aperçu avant publication |
| **P1 — Fatigue et récupération dans le suivi** | Organiser l'entretien à partir de sensations répétées et de leur contexte, plutôt que d'une seule courbe | debrief, questionnaires, RMSSD et mesures HRV, items pertinents ; B | M ; mapping questions, baseline individuelle, règles de fraîcheur | HRV non comparable entre protocoles, biais de déclaration, données sensibles ; sources/conditions visibles, pas score récupération inventé |
| **P1 — Alertes charge excessive/insuffisante avec confiance** | Une liste courte de situations à examiner, avec les preuves et les manques | Volume, intensités, provenance de charge, tendances CTL/ATL/TSB, retours ; B | L ; historique suffisant, calibration coach et contrôle faux positifs | Pas de diagnostic de surentraînement/blessure ; vocabulaire « signal à examiner », confiance abaissée si incomplet ; aucune décision automatique |
| **P1 — Progression des performances** | Comparer efforts réellement comparables et vérifier si le plan produit les adaptations attendues | Records catalogués, sport/source, laps/streams à la demande, tests TFCLab ; B | M ; unités, méthodes de sélection, qualité capteurs | Records opportunistes, météo/parcours/état de fatigue ; séparer « meilleur effort observé » et « capacité physiologique estimée » |
| **P1 — Semaines de charge et récupération individualisées** | Proposer une semaine récupératrice ou une progression compatible avec ce que l'athlète a effectué | Historique par discipline, réponses, objectifs et contraintes TFCLab ; B | L ; réutiliser rampes de volume et individualisation existantes, sans remplacement par PMC | Doubler les règles déjà présentes, imposer une adaptation IA ; règles expliquées et choix coach, aucune refonte moteur |
| **P1 — Objectifs intermédiaires** | Relier courses B, tests et étapes du cycle à l'objectif A ; discuter les écarts sans déplacer l'objectif final seul | planned/real competitions, goal_type, cycles, dates, performances/tests ; A/B | M ; rapprochement objectifs locaux/distants, synchronisation cycles | Événement déplacé dans Nolio écrasé ; conflit explicite et provenance des dates |
| **P1 lecture / P2 écriture — Zones et compétitions** | Éviter de prescrire avec des zones obsolètes et garder les courses visibles dans les deux outils | zones/final, wrappers, metrics, planned/real competitions ; A/B, forme targets C | M/L ; version de zones, doctrine, permissions settings:write uniquement si requis | Un numéro de zone ne signifie pas LT1/MLSS ; proposition avec comparaison des bornes et approbation avant mutation |
| **P1 fondations / P2 ouverture — Multicompte et multi-athlète** | Un coach retrouve ses athlètes sans mélanger les données ; plusieurs coachs externes peuvent connecter leur propre Nolio | Applications partenaire OAuth ou équipe, me, athletes/groups, app/users ; A/B | L ; isolation tenant, refresh, consentements, examen partenaire Nolio, support utilisateurs | Cross-tenant, limite dev 5 comptes, délégations incorrectes ; tests d'isolation et aucune clé partagée implicitement |
| **P2 — Bibliothèque de séances validées** | Réutiliser les séances fiables du coach et réduire la ressaisie, sans publier une version non approuvée | library training_frames/exercises/plan_frames, search/content/apply ; A/B, workouts détaillés C | M/L ; politique de version, rôles d'équipe, mapping local/distants | Assistant sans accès à bibliothèque équipe, propagation de changements ; valider versions et droits, pas d'activation automatique |
| **P2 — Analyses fines d'exécution des intervalles** | Comparer les répétitions réellement effectuées aux cibles approuvées pour choisir le prochain travail | workouts complets + streams/laps ; B et C pour alignement précis | L ; protocole nœuds, capteurs autorisés, qualité temporelle, annotation des laps | Chronologie manquante, auto-laps multiples, restriction fichiers ; confidence et contrôle d'alignement plutôt qu'un score de conformité arbitraire |

La priorité P0 va à la fiabilité de publication et à la lecture compréhensible. Les alertes et adaptations gagnent leur utilité après preuve d'exhaustivité, qualité et contextualisation ; l'existence des endpoints PMC/HRV ne suffit pas à justifier une décision de charge.

## 4. Mesure de réussite proposée

- Export : aucune séance publiée sans approbation attachée au contenu ; aucun doublon lors d'un double clic ; tous succès partiels visibles ; aucune modification distante écrasée sans décision.
- Tableau de bord : chaque valeur possède unité, source, date de collecte et couverture ; courses incluses ; « inconnu » distinct de zéro ; activités sans planned visibles.
- Analyse : chaque proposition cite les observations et les hypothèses, précise les manques et conserve un niveau de confiance compréhensible ; le coach peut la rejeter sans mutation du calendrier.
- Exploitation : fin d'accès suspendue immédiatement et purge démontrée dans le délai ; budgets de quotas observés ; aucune donnée sensible dans les logs techniques.

Hors feuille de route initiale : billing, vente de plans marketplace, invitations ou changements de membres, messagerie proactive, écriture des réalisés/HRV. Leur ajout demanderait une valeur produit, un périmètre d'accès et une validation distincts ; cet audit ne les autorise pas.
