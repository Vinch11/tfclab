## 3. Diagnostics d'échec assainis

Une projection partagée filtre les erreurs avant SSE et console. Elle exclut
réponse modèle, extraits rawFirst800/rawLast400, messages d'exception libres,
configuration, noms/objectifs libres, données médicales et jetons d'accès.
Elle garde codes techniques connus, indices de chunk/semaine, chemins de
validation limités aux champs du schéma, compteurs, nombre de réparations,
finish reason et contraintes explicites reconnues.

Le client conserve désormais les avertissements techniques et contexte de
version aussi quand le JSON échoue. Avant journalisation, stockage local,
miroir statistique existant et export, les entrées sont reconstruites par
liste de champs autorisés. L'ancien historique est également projeté à la
lecture : aucun effacement de données athlètes ni migration. Les compteurs
value_check_summary restent exploitables par B9, sans leurs textes libres.

Sur `/debug/plan-qa`, « Exporter diagnostics assainis (sans sauvegarde) »
produit un JSON local, sans requête de génération et sans sauvegarde du plan.
Le rapport complet de stats emploie la même projection. Ce diagnostic est
borné aux50 dernières entrées ; il n'est **pas** une archive du plan brut,
du payload athlète ou de toutes les séances. Une éviction du stockage Safari
ou un échec d'écriture local peut encore faire perdre ces traces.

Les erreurs restent bloquantes selon les mêmes protections sportives :
aucune sévérité ni prescription n'est abaissée. Les retries existants ne
changent pas. Les tests canaris couvrent console, SSE mocké, historique
legacy, stockage, export et données médicales injectées dans un faux retour.

## 4. Artefacts, contrat et reproductibilité

Commande de préparation (aucun déploiement) :

```
TFCL_DENO_BIN=deno node scripts/preproduction/prepare-plan-release.mjs --commit <SHA_APPROUVE> --out /tmp/release-a
TFCL_DENO_BIN=deno node scripts/preproduction/prepare-plan-release.mjs --commit <MEME_SHA> --out /tmp/release-b
node scripts/preproduction/verify-plan-release.mjs /tmp/release-a/manifest.json /tmp/release-b/manifest.json
```

Le script refuse un répertoire de sortie non vide. Il extrait le commit via
`git archive`, sans embarquer des changements de worktree. Les dépendances
frontend doivent avoir été installées avec le lockfile figé ; la CI fait
`bun install --frozen-lockfile`, Bun1.3.0, Node24.19.0, Deno2.9.6 linux-x64.
L'installation peut contacter les registres ; compilation/test n'appelle
aucun modèle ni service athlète. Les tests Deno locaux peuvent ensuite être
exécutés avec cache seul. Le lock runtime Edge est limité aux fonctions,
indépendamment du graphe npm de développement du frontend.

Le manifeste contient :
- commit source, époque Git, version du manifeste ;
- empreinte des sources du contrat JSON/règles partagées/normalisation/
  sizing/sérialisation (liste explicite dans le script) ;
- SHA256 du **catalogue effectif** exporté offline depuis WorkoutLibrary,
  tri canonique des fiches et propriétés, pas seulement le hash d'un fichier ;
- empreinte des lockfiles/package, toolchain et source archive ;
- SHA256 et taille des trois archives : frontend, ai-training-plan,
  ai-training-plan-test. Les références rollback restent null/non attestées
  tant que les métadonnées fournisseur manquent.

Le frontend est réellement compilé par Vite/PWA. Les deux fonctions sont
bundlées sans exécution avec Deno, imports locaux/partagés et bibliothèques
HTTP/npm inclus, dépendances figées par edge-dependencies.lock. Les builtins
node:/Deno restent fournis par le runtime cible : sa compatibilité réelle
ne sera pas prétendue testée sans environnement et version attestés.

Les horodatages frontend et des archives sont déterministes depuis le commit
(NODE_ENV production explicite, SOURCE_DATE_EPOCH, TZ UTC, ordre/permissions/uid/gid/mtime tar fixes).
Le préchargement SSR ne doit pas activer du JSX de développement contenant
des chemins temporaires ; le préparateur refuse un tel résultat. Deux constructions
isolées doivent donner des SHA identiques. Le vérificateur refuse une archive
altérée, un mélange de commits/contrats/catalogues ou un catalogue modifié,
même si des tailles paraissent correctes. Le workflow dédié publie les trois
artefacts de préparation et le manifeste comme preuve CI, pas vers Lovable
ou Supabase. Les SHA effectifs figurent dans ce manifeste et la description
PR, pour éviter une référence Git circulaire manifeste→commit→manifeste.

## 5. Attestation de release et refus avant coût

Le source Git porte une attestation **non construite** (`attested:false`),
pas un SHA fabriqué. Le préparateur remplace ce template uniquement dans
son archive de build et injecte la même identité dans Vite et les fonctions.
Les artefacts embarquent leurs métadonnées techniques.

Un GET `?release=1` est préparé sur chaque fonction : lecture de métadonnées
techniques uniquement, jamais de DB ou modèle. Il retourne503 pour un source
non attesté. Les contrôles du gateway JWT existant ne sont pas désactivés.
Ces routes ne sont pas déclarées déjà déployées ni sondées en production.

Un frontend attesté vérifie la release du serveur sélectionné avant tout
POST payant. Les headers techniques source/contrat/catalogue sont ensuite
vérifiés côté serveur avant lecture des données athlètes ou génération. Un
serveur non construit retourne503 ; une version mélangée retourne409.
Aucune compatibilité ancienne/nouvelle n'est supposée silencieusement. Le
développement et les fixtures locales restent distincts d'une release
attestée. Le refus de version n'appelle pas Gemini et conserve l'auth ensuite.

Lovable doit compiler la même source et les mêmes métadonnées de build,
ou publier l'artefact préparé par un mécanisme réellement disponible. Cette
capacité n'est pas attestée dans la session ; publier par le build ordinaire
sans manifeste ne suffit pas et bloque la génération plutôt que de prétendre
être une release vérifiée. Après squash/commit différent, reconstruire les
**trois** artefacts et leurs empreintes : ne pas réétiqueter les anciens.

## 6. Vérifications et risques résiduels

Tests ciblés : refus d'archives corrompues/mélangées, contrôle de version
GET/POST sans lecture du corps, double refus JSON mocké sans fuite médicale,
conservation des raisons techniques et des compteurs QA. Suites complètes
frontend, Deno deux miroirs et CI : résultats dans la description PR.

Le contrôle supplémentaire `deno check` des index est maintenant vert : les
anciennes références `full` invalides ont été corrigées en `fullPlanText`,
le tampon déjà utilisé par le même contrôle LCW. Aucune suppression de
protection ; le diagnostic LCW legacy peut désormais réellement s'exécuter.

Risques : anciens clients bloqués tant que les trois versions ne sont pas
alignées ; cache PWA ; GET de précontrôle dépendant du réseau ; capacité de
publication Lovable non attestée ; runtime Edge inconnu ; déploiements et
rollback historiques inconnus ; dépendances runtime builtin ; stockage local
borné/évictable. Les refus JSON stricts peuvent augmenter les retries, délais
et coûts si le pool/les variantes restent insuffisants. Les protections
sportives, les variantes non vérifiées et les limites de qualité de #405
restent applicables ; aucun test ne certifie un programme complet réel.

## Verdict

**NO-GO pour la production et une génération payante.** Les artefacts et
preuves offline permettent de préparer une release cohérente, mais ne
remplacent pas les attestations et sauvegardes de rollback manquantes, ni
un contrôle du runtime/publication cible. La réussite des constructions et
CI sera rapportée séparément de cette décision opérationnelle.

Prochaine décision requise : examiner la PR et ses preuves, fournir un accès
en lecture ou les exports de métadonnées manquants, puis décider séparément
fusion et déploiement coordonné. Aucune fusion, publication, génération
réelle, écriture athlète, migration ou opération Nolio pendant P3. Arrêt de
la mission après livraison ; aucune suite engagée automatiquement.
