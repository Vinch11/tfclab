# Export Nolio du coach DET

`node release/det/build-nolio-backend.mjs <dossier>` prépare dans un dossier neuf un projet Supabase limité à DET. Il réutilise le client Nolio V2 du dépôt et le journal des opérations. Les fonctions se nomment `det-nolio-connect`, `det-nolio-callback` et `det-nolio-export`. Chacune importe ses modules communs depuis `supabase/functions/_shared/det-nolio-v2` et peut être livrée séparément. Les tables et procédures de la migration portent le préfixe `det_nolio_v2_`, les index le préfixe `det_nv2_`. Le coach associe le calendrier de l’athlète.

Le projet Supabase de TFCLab 2.1 est géré dans Lovable. La migration y a été appliquée et les trois fonctions y répondent depuis le 11 novembre 2026. Sur un nouveau projet, appliquer la migration produite une fois, configurer `NOLIO_V2_CLIENT_ID` et `NOLIO_V2_CLIENT_SECRET`, puis déployer les trois fonctions. Le callback enregistré pour cette application Nolio doit correspondre à `https://<projet>.supabase.co/functions/v1/det-nolio-callback`. Le coach autorise ensuite les droits de lecture et écriture des séances dans **Compte et athlète Nolio**. Les droits, les tokens et les créations sont conservés côté serveur. [Journal de recette](evidence/parcours-publie.json)

**Exporter le plan**, **la semaine** et **la séance** archivent la version datée pour l’athlète sélectionné. Le serveur refait le précontrôle avec les références Nolio de cet athlète, compose les deux parties d’un enchaînement, puis utilise la simulation de Nolio avant chaque lot. Une sélection contenant une séance refusée bloque l’envoi de cette sélection. Une opération incertaine conserve son état dans le journal. Réessayer la même sélection réutilise les opérations déjà confirmées. La relecture finale compare les étapes des activités présentes dans Nolio. La réception matérielle se vérifie ensuite sur la montre appairée.

Sur la branche principale du site, le workflow GitHub **DET — déployer les fonctions Nolio** offre aussi un déploiement de ces trois points d’entrée depuis GitHub lorsqu’un secret de déploiement Supabase y est configuré. La consultation de l’état HTTP démontre la présence du service. La preuve d’un envoi réel conserve la date, la version de plan, la séance et l’identifiant d’activité renvoyé par Nolio, puis le même identifiant à la relecture.
